# 品質の警告を利用者に見せるのは CLI 自身の 1 行だけにする

- 日付: 2026-09-20
- 状態: 受理（ADR-0009 が決めなかった「誰が表示するか」を決める）

ADR-0009 は、品質を診断値として結果に記録し、閾値を割ったものは
`NumericalQualityWarning` で発報し、同じ文言を `messages` にも残す、と決めた。
`report_quality` はこれを 3 つの行き先へ流している。

| 行き先 | 誰のためか |
|---|---|
| `warnings.warn` | ライブラリとして使う人への通知。notebook でも目に入る |
| `logger.warning` | 実行の痕跡。`--log` のファイルに残る（ADR-0052） |
| 戻り値 → `Diagnostics.messages` | 結果そのものの一部。結果ファイルに書かれる（ADR-0010） |

文言は 1 種類しかない。3 つは同じ文を別の相手に届けるための別の経路である。

決めていなかったのは**誰が利用者の画面に出すか**だった。CLI は結果を受け取った後に
`Diagnostics.messages` を読んで `warning: ...` と自分の書式で出す。ところが CLI は
同時に「`warnings` を受け取るアプリケーション」でもあるので、`warnings` の既定の表示も
素通りする。結果、同じ文言が 2 度、しかも片方は
`src/fcenvelope/cli.py:370: NumericalQualityWarning:` と実装のファイル名・行番号・
ソースの断片つきで出ていた。利用者にとって意味のない情報である。

**CLI が利用者に見せるのは `_echo_warnings` の 1 行だけとし、`warnings` の表示は
アプリケーションの入口で 1 度だけ降ろす。**

```python
@app.callback(invoke_without_command=True)
def main(...) -> None:
    warnings.filterwarnings("ignore", category=NumericalQualityWarning)
```

## なぜ「表示を降ろす」でよいのか

`warnings.warn` は出力そのものではなく、**表示するかどうかをアプリケーションが決める
ための仕組み**である。ライブラリが上げ、アプリケーションがフィルタで決める、という
分担が `warnings` の設計そのものなので、自分で同じ内容を出すアプリケーションが表示を
降ろすのは想定された使い方である。この 1 行がその決定にあたる。

置き場所が `@app.callback` なのは、これが**副命令ごとの都合ではなく CLI という 1 つの
アプリケーションの方針**だからである。実行のたびに区画で包むと、方針が実行の途中に
あるように読めるうえ、包んだ範囲の中で起きた関係のない警告まで巻き込む。

`logger.warning` と `Diagnostics.messages` は `warnings` のフィルタとは別の経路なので、
`--log` のファイルにも結果ファイルにもそのまま残る。**出力ファイルだけを後から見て
信頼可否を判定できる**という ADR-0009 の要はここに乗っている。

## 表示の出どころを `Diagnostics.messages` に寄せる理由

CLI が読むのは結果の診断値であって、`warnings` ではない。CLI が報告するのは
**いま書き出したファイルの品質**だからである。保存済みの結果を読む経路（`script`）では
計算が走らないので `warnings` は一度も上がらないが、診断値はファイルの中にある。
経路によって見えたり見えなかったりしない側を出どころに選ぶ。

## 検討した選択肢

- **`warnings.showwarning` を差し替え、`_echo_warnings` をやめる**: 経路は 1 本になるが、
  出どころが `warnings` になる。保存済みの結果を読むだけの実行では何も出なくなり、上の
  理由に反する。表示の時機も計算の最中になり、`wrote ...` の後に注意書きが並ぶ順序が崩れる。
- **`report_quality` から `warnings.warn` を外す**: 二重化は根元から消えるが、ライブラリ
  として使う人が戻り値を見ない限り何も気づけなくなる。`warnings` はそのための仕組みなので、
  外すのは失うものが大きい。
- **副命令の本体を `catch_warnings` で包む**: 効きはするが、1 つの方針を実行のたびに
  述べ直すことになる。包んだ範囲に関係のない警告まで入るのも意図と違う。

## 帰結

**計算する副命令は、必ずその結果の `messages` を報告する。** 報告しない経路で計算すると
警告が誰にも見えなくなる。今は `run` と `lines` の両方が `_report_any` を通っており、
`test/test_cli.py` が「同じ文言がちょうど 1 度だけ、実装のファイル名なしで出る」ことを
見ている。副命令を足すときはこの規則に入れる。
