# 版は `pyproject.toml` に書き、git タグをそれに合わせる

- 日付: 2026-09-20
- 状態: 受理

版番号は `pyproject.toml` の `version` に書く。リリースは、その版に一致する git タグ
`vX.Y.Z` を打つことである。**書かれた版が唯一の情報源で、タグはそれを指す印である。**

```toml
[project]
version = "0.1.0"
```

```bash
git tag -a v0.1.0 -m "v0.1.0"
```

これまで `version = "0.1.0"` は置かれていたが、1 度も動かされておらず、タグも無かった。
結果ファイルの来歴（`fcenvelope_version`、ADR-0046）に書き込まれる版が、どの時点の
コードを指すのかを確かめる手段が無い状態だった。

## 番号の意味

`X.Y.Z` を semantic versioning として読む。ただし本プログラムで「互換性」が問題になるのは
利用者から見える 3 つの面だけなので、その 3 つで判定する。

| 面 | 具体 |
|---|---|
| 公開 API | `fcenvelope.__all__` にある名前とその引数 |
| CLI | 副命令・オプション・既定の出力ファイル名 |
| ファイル形式 | 入力ファイルと結果ファイル（`schema_version`） |

- **Z（patch）**: 上の 3 つが変わらない修正。計算結果の数値が変わらない不具合修正、
  文書、テスト、内部の整理。
- **Y（minor）**: 上の 3 つに**足す**変更。新しいオプション、新しい流儀や単位、
  新しい入力項目。既存の入力ファイルとスクリプトがそのまま通ること。
- **X（major）**: 上の 3 つから**取り上げる**か、意味を変える変更。

`schema_version` はファイル形式の版であって、パッケージの版とは別の数である
（ADR-0040）。形式が 3 のまま `0.1.0` → `0.2.0` と進むことも、形式だけが 3 → 4 に
上がることもある。両者を連動させない。

**計算結果の数値が変わる変更は、それだけで Y 以上とする。** 不具合修正であっても、
同じ入力から前と違う数が出るなら利用者の手元の図が変わる。patch にはしない。

1.0.0 は「公開 API・CLI・ファイル形式をこれ以上むやみに動かさない」と決めたときに
打つ。それまでは 0.Y.Z で、Y が上の表の major と minor を兼ねる。

## タグからは導かず、書いた版を読む理由

版をタグから導く仕組み（`hatch-vcs` など）もあり、番号を 1 か所しか書かずに済むという
利点がある。採らない。理由は 3 つある。

**CI が落ちる。** `.github/workflows/test.yaml` の `actions/checkout` は既定で深さ 1 の
取得をするので、チェックアウト先にタグが無い。タグから導く仕組みはそこで版を決められず、
`fetch-depth: 0` を足して回る必要が出る。ワークフローを触らずに済ませたい。

**`uv sync --locked` が止まる。** `uv.lock` は本体の版も記録している（ADR-0066 の
`--locked`）。版が git の状態で決まると、同じ木から違う版が出てきて lock と食い違いうる。
書いた版なら lock と必ず一致する。

**git の無い木で配れなくなる。** sdist を解いた木や、リポジトリを zip で落とした木には
`.git` が無い。そこで版が決まらないのは、来歴を書き込む本プログラムにとって困る。

代わりに、書いた版とタグがずれる危険を**テストで見る**（`test/test_version.py`）。
`pyproject.toml` の版・`fcenvelope.__version__`・`CHANGELOG.md` の最新見出しの 3 つが
一致することを確かめるので、版を上げ忘れた組み合わせは CI で止まる。タグ自体は
リリースの最後に打つので、手順書（`docs/dev/release.md`）の側で見る。

## `CHANGELOG.md` を置く理由

番号だけでは、`0.1.0` と `0.2.0` の間に何が起きたのかが分からない。利用者が自分の入力
ファイルを直す必要があるかどうかを判断する場所が要る。

[Keep a Changelog](https://keepachangelog.com/) の形に倣い、版ごとに「追加 / 変更 /
修正 / 削除」で書く。書く相手は利用者なので、**利用者から見て何が変わったか**を書く。
内部の整理は書かない。それは ADR と git の履歴が持つ。

未リリースの変更は `## 未リリース` の下に積み、リリースのときに版番号の見出しへ変える。

## リリースを自動化しない理由

PyPI へは出しておらず、配布は `git clone` と `uv sync` である。出す先が無いので、
タグを起点にビルドして公開するワークフローは置かない。リリースは `docs/dev/release.md`
に書いた手順を人が実行する。

後で PyPI へ出すことになったら、そのときにワークフローの導入を決める ADR を起こす。
