# ゴールデンケースはディレクトリ 1 つに入力ファイルと参照データの CSV を置く

- 日付: 2026-09-24
- 状態: 受理

これまでのテストは解析解（単一モード・T = 0 の Poisson 級数など）と、モーメントや総和のような
恒等式で計算を確かめてきた。多モード・有限温度のように解析解の無い系では、外部の類似
プログラムの出力と突き合わせるしかない。その参照データをリポジトリに置き、`uv run pytest`
で毎回比べる。

**ゴールデンケースは `test/golden/<ケース名>/` のディレクトリ 1 つで表す。中身は本プログラムの
入力ファイル `input.toml`、ケースの記述 `case.toml`、参照データの CSV である。**

```
test/golden/<ケース名>/
  case.toml       出どころ・比べる表現・許容差・CSV の列
  input.toml      本プログラムの入力ファイル（参照データと同じ条件）
  envelope.csv    エンベロープの参照データ（比べるときだけ）
  lines.csv       線の参照データ（比べるときだけ）
```

```toml
[source]
program = "<外部プログラム名>"
version = "<版>"
note = "<計算の条件や、出力をどう整形したか>"

[envelope]
csv = { path = "envelope.csv", columns = [["energy", "eV"], "density"] }
tolerance = 1e-3

[lines]
csv = { path = "lines.csv", columns = [["energy", "cm^-1"], "weight"] }
energy_tolerance = [0.01, "cm^-1"]
tolerance = 1e-4
```

## 決まりごと

- ケースは `test/golden/` の下で `case.toml` を持つディレクトリを数え上げる。足せば自動的に
  検証される（ADR-0056 の例と同じ考え方）。
- 計算の条件は `input.toml` だけに書き、`case.toml` には書かない。入力ファイルそのものなので、
  `fcenvelope run` / `lines` にそのまま渡せる。書式は TOML だけにする（ADR-0069）。
- `[source]` の `program` は必須、`version` と `note` は任意。比較には使わず、後から読む人の
  ための記録である。
- `[envelope]` と `[lines]` の少なくとも一方を書く。書いた表現だけを比べる。
- CSV の書き方は入力ファイルの `modes.csv` と同じ（ADR-0079）。`columns` で列の並びと単位を
  書き、`["energy", "eV"]` のように倍率・別名も含めて入力と同じ単位が使える。`columns` を
  省けば、ヘッダがあればその並び、無ければ `energy` が先で単位は cm⁻¹ である。
- エネルギーは本プログラムの E 軸で書く。ZPL が 0 で、振動量子を生成するサイドバンドが負側
  （ADR-0004）。外部プログラムが吸収の向きや絶対エネルギーで書いていれば、整形のときに直す。
- エンベロープの列は `energy` と `density`。`density` の大きさは問わない。計算結果を参照の点へ
  線形補間し、両方を参照の点の上で面積 1 に正規化してから比べる。ずれは差の絶対値の最大を
  参照の最大値で割ったもので、`tolerance` 以下なら一致とする。参照の点は計算の出力窓
  （`grid.e_min` / `grid.e_max`）の内側に収める。
- 線の列は `energy` と `weight`。重みは本プログラムの定義どおり、FC 因子に始状態の熱占有を
  掛けた、全遷移の和が 1 になる数で書く。エネルギーの差が `energy_tolerance` 以下の線は
  参照・計算の両方をまとめて 1 本とし、重みの和を比べる。片方にしか無い線はもう片方を 0 と
  する。差の絶対値がどの線でも `tolerance` 以下なら一致とする。
- `density` と `weight` には単位を添えない。
- 比べる計算で品質警告（`NumericalQualityWarning`）が出たら失敗にする。

## 理由

**入力ファイルをそのまま置く。** ケースの条件を別の形で書くと、入力ファイルとの対応を
テストが持つことになり、入力の形を変えるたびにそちらも直すことになる。入力ファイルなら
形の変更は ADR-0040 の方針どおり書き換えるだけで、CLI で同じ計算を手元でやり直せる。

**参照データは CSV にする。** 外部プログラムの出力は数千行の表になりうる。表計算やスクリプト
で整形しやすく、差分も行単位で読める。結果ファイル（JSON）の形にしないのは、`conditions` や
`diagnostics` のように外部プログラムからは作れない欄を持つためである。列と単位の書き方は、
入力の CSV と同じにしたので新しく覚えることがない。実装も `inputs.read_csv_table` と、それと
組にして公開した `inputs.csv_columns` を使う。

**エンベロープは正規化して形を比べる。** 外部プログラムのスペクトルは縦軸が任意単位のことが
多い。本プログラムの規格化（∫F dE = 1）は `total_area` の診断値と既存のテストが確かめている
ので、ここで見るべきは形である。両方を同じ点の上で正規化するので、参照が出力窓の一部しか
含まなくても、窓の外に逃げた面積の分だけずれることはない。

**線は重みの絶対値で比べ、エネルギーでまとめる。** 重みは無次元で総和が 1 と決まっている
ので、正規化せずに比べられる。遷移のラベルの付け方（モードの番号、縮退した線を分けるか
まとめるか）はプログラムごとに違うので、ラベルでは突き合わせず、エネルギーで同じ線と
みなす。片方にしか無い線を 0 と比べるので、両方の打ち切り（本プログラムでは
`selection.min_weight`、外部プログラムではその閾値）が `tolerance` 以下なら、打ち切りの違いで
失敗することはない。

**品質警告を失敗にする。** ゴールデンケースは「この条件なら本プログラムの数は信じられる」と
いう前提で外部プログラムと比べる。警告が出る条件で一致・不一致を見ても、どちらの問題かが
分からない。

## 採らなかった案

- **エネルギーの原点や符号を `case.toml` で指定する。** 外部プログラムごとの流儀を読み替える
  つまみはいくらでも増える。整形はリポジトリに入れる前に一度だけ行えば済むので、参照データは
  本プログラムの E 軸で書くことにした。
- **スペクトルに掛かる周波数の因子（吸収の ω、発光の ω³）を外す。** 本プログラムはこれを
  扱わない（ADR-0001）。参照データはこの因子を含まない FC の線形状で書く。
- **ケースの比較をパッケージの機能（CLI の副命令）にする。** 使うのはテストだけなので、比較は
  `test/test_golden.py` に置く。
