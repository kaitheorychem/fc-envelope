# 単位の軸を項目ごとに独立させ、全体で 1 つの単位にはしない

- 日付: 2026-09-17
- 状態: 受理（ADR-0002 の「検証点だけ用意する」を、実際に変換を入れる形へ進める）

単位変換を入れるにあたり、**1 つの単位指定がどこまで効くか**を決める必要がある。入力
ファイル全体で 1 つの `energy_unit` を持つ案は採らない。次の 4 つを独立した軸とする。

| 軸 | 何の単位か | 既定 |
|---|---|---|
| `frequency_unit` | `modes[].frequency` | `cm^-1` |
| coupling の単位 | `modes[].coupling`。無次元の流儀では指定してはならない（ADR-0033） | 流儀による |
| `broadening` の単位 | σ | `cm^-1` |
| `grid` の単位 | `e_min` / `e_max` / `de` | `cm^-1` |

描画の横軸の単位も、これらとは別の軸になる。当面は `cm^-1` 固定で据え置き、決めるのは
単位変換が入った後にする。

## 理由

coupling は**他のプログラムが計算した値をそのまま持ち込む**のが基本であり、その単位は
相手側の都合で決まる。基本方針は「相手のプログラムの単位に合わせて受け取る」で、明示的に
単位が指定されたときだけ別の単位として読み、計算に入る前に変換する。

いっぽう frequency はほぼ常に `cm^-1` である。したがって **coupling と frequency の単位が
揃うことは前提にできない**。σ とグリッドはさらに出どころが違い、利用者が計算窓として選ぶ
量である。この 3 者を 1 つの指定で縛ると、どれかを相手の都合に合わせた瞬間に他が巻き添えで
動く。

σ とグリッドは同じエネルギー軸上の量だが、指定はブロックごとに分けて持つ。

## 検討した選択肢

- **全体で 1 つの `energy_unit`**: `frequency_unit` の意味が変わるため破壊的変更
  （`schema_version` 3）になる。そのうえ coupling の単位が相手プログラム由来である以上、
  揃えること自体ができない。
- **`frequency` と `coupling` を同じエネルギー単位に揃える規約**: ADR-0033 が「V を eV^1.5
  で、ω を cm⁻¹ で与えてよいのか」として立てた問いへの、もう一方の答え。frequency が
  `cm^-1` に固定されている実態と噛み合わないので採らない。

## 帰結

単位フィールドはすべて省略可で、省略時の既定値は現行の `cm^-1` である。既存の入力ファイル
はすべて有効なままなので、`schema_version` は 2 に据え置く（ADR-0019 と同じ上位互換の追加）。

ADR-0033 が `energy_power` の説明に書いた「coupling と frequency を同じエネルギー単位で
表しておけば変換式の中で次元が打ち消し合う」という前提は成り立たない。両方をそれぞれの
単位から正準単位へ変換したうえで変換式に入れる（ADR-0054）。`src/fcenvelope/units.py` の
`energy_power` の docstring と `docs/dev/spec/interface.md` の対応する記述を改める。
