# 入力ファイルの雛形はパッケージが持つ TOML で、CLI がそれを書き出す

- 日付: 2026-09-22
- 状態: 受理（雛形を実物のファイルとして持つのは ADR-0059 と同じ、既にあるものを潰さない
  のは ADR-0060 と同じ）

入力ファイルを書き始めるには、今のところ `docs/readme/usage.md` か
`docs/readme/examples/` から写してくるしかない。**入力ファイルの雛形を書き出す副命令
`fcenvelope template` を置く。**

```
fcenvelope template              # 端末に出す
fcenvelope template -o input.toml   # ファイルに書く（既にあれば残す）
```

雛形は `src/fcenvelope/templates/input.toml` に**実物の TOML ファイル**として置き、
生成は読んで書くだけである。項目には 1 行のコメントが付き、その行が**何を設定する数か**
だけを言う。規則そのもの（単位表・流儀・グリッドの取り方・診断値の読み方）は
`docs/readme/usage.md` にあり、雛形はそちらを指すだけで繰り返さない。

## 理由

**この雛形が答えるのは「入力ファイルに何が書けるか」である。** 実運用の条件は別に置く
テンプレート置き場で決めるものなので、プログラムが書き出す雛形に、効く値の組み合わせや
条件の作り込みを入れない。したがって載せるのは項目の一覧と、それぞれが何の数かという
1 行だけで、値は文書の基本例と同じものを置く。

**コメントが雛形の中身なので、書式は TOML だけである。** JSON にコメントは書けず、
コメントを落とした雛形は `docs/readme/examples/` の例と変わらない。`-o` に `.json` を
渡したときは書かずに使用法エラーで止める。入力ファイルとしての JSON は今までどおり
読める（ADR-0069）。

**実物のファイルとして持つのは作図スクリプトの雛形と同じ理由である**（ADR-0059）。
文字列を組み立てて作ると、雛形そのものが壊れていても配るまで分からない。実物なら
テストが直接読んで、パースできること・そのまま計算が通ること・スキーマの項目を
取りこぼしていないことを見られる。

**既にあるファイルは黙って潰さない**（ADR-0060）。書きかけの入力ファイルは手で書いた
ものなので、`kept ...` と言って残し、`--force` でだけ上書きする。

## 検討した選択肢

**スキーマから生成する**: pydantic のモデルから項目を数え上げて組み立てれば、項目が
増えたときに雛形が自動で追随する。採らない理由は、この雛形の値打ちが**コメントの文面**
と項目の並び順にあることである。どちらもモデルからは出てこないので、結局それらを
モデルの側に書き足すことになり、入力ファイルの型に文書の責務が移る。追随は生成ではなく
テストで留める（`test/test_template.py` が型の側から項目を数え上げて、雛形が触れて
いることを見る）。

**`run` のオプション（`--write-template`）にする**: `run` は入力ファイルを引数に取る
副命令なので、入力ファイルがまだ無いときの仕事をそこに置くと引数の要不要が噛み合わない。
`script` と同じく、独立した副命令にする。

**既定でファイルに書く（`input.toml`）**: 引数なしの実行が作業ディレクトリにファイルを
作るのは、見るだけのつもりで打ったときに驚きがある。既定は端末で、`>` でも `-o` でも
ファイルにできる。

## 帰結

副命令が 1 つ増える。`template` は計算も入出力の追跡もしないので `--log` は取らない
（痕跡を残すべき節目がなく、痕跡の置き場にする出力もまだ無い）。

`inputs.template_text()` が雛形のテキストを返す。入力ファイルの書式を知っているのは
`inputs.py` なので、雛形もそこから配る。作図スクリプトの雛形（`emit.py`）とは配る
相手が違うだけで、持ち方は同じである。

項目を足すときは、入力ファイルの型・`usage.md` の表に加えて**雛形にも 1 行足す**。
忘れれば `test/test_template.py` が落ちる。
