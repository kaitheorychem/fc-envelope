# 入力ファイルは TOML を基本とし、JSON は実効設定を読み返す側に残す

- 日付: 2026-09-20
- 状態: 受理（ADR-0005 の「入力は 1 ファイルの JSON」を書式の面から改める。ファイルの**構造**は ADR-0035 / 0040 / 0053 のまま）

入力ファイルの書式を TOML と JSON の 2 つにする。どちらで書いても読んだ後は同じ辞書に
なり、検証・正準化・計算・出力は書式を知らない。文書の例は TOML で書く。

```toml
schema_version = 2
frequency_unit = "cm^-1"
coupling_convention = "g"
temperature = 300.0

[[modes]]
frequency = 1200.0
coupling = 0.5

[broadening]
sigma = 150.0

[grid]
e_min = -4000.0
e_max = 1000.0
de = 5.0
```

入力ファイルは**人が手で書くもの**である。モードの並びと計算条件が同居していて、条件の
ほうは何度も書き換える。JSON はこの用途に向いていない——末尾のカンマが書けず、コメントが
書けず、括弧の対応を目で数える必要がある。単位や流儀の選び方は書いた本人にも半年後には
思い出せないので、入力ファイルにコメントを書けることには実際の値打ちがある。

TOML を選ぶのは、Python 3.11 から `tomllib` が標準ライブラリにあり依存が増えないこと、
`[[modes]]` の表の並びが行指向のモードデータ（ADR-0005）とそのまま重なること、
`pyproject.toml` で既に使っている書式なのでこのリポジトリを触る人には馴染みがあることによる。
YAML は依存が増えるうえ、`NO` が偽になる類の暗黙の変換があり、外部プログラムから
そのまま貼り付けた数値の意味が変わりうるので採らない。

## JSON を残す理由

実効設定（ADR-0065）は JSON で書き出し続ける。これは**機械が書いて機械が読み返す**
ファイルで、書きやすさは関係がない。TOML には `null` がなく、`coupling_unit` と
`selection.max_quanta` の「無し」を書けない。実効設定は「省略された項目が既定値で埋まって
いる」ことが取り柄なので、埋めた結果が書けない書式では名目が立たない。

したがって JSON の役割は「生成された正準化 JSON を読み返して再実行する」ことであり、
入力を手で JSON で書くことは妨げないが、文書がそちらを勧めることはしない。

## 書式は拡張子だけで決める

`.toml` と `.json` で振り分け、中身は見ない。知らない拡張子はその場でエラーにする。
中身から推測すると、書き損じた TOML が JSON として読まれて的外れな位置で失敗するなど、
誤りの報告が読みにくくなる。拡張子は利用者が書式を宣言する場所である。

振り分けの表は `inputs.INPUT_FORMATS` の 1 か所にあり、書式を足すのはそこへの 1 行で済む
（ADR-0049）。

## 帰結

- 既定の出力名は入力ファイルの拡張子を除いた部分から作るので（ADR-0063）、
  `fcenvelope run input.toml` の出力は `input_envelope.json` になる。結果ファイルは
  従来どおり JSON で、書式の選択は入力の側にしかない。
- `--override` の値は入力ファイルの書式によらず JSON として読む（ADR-0064）。TOML には
  `null` がないので、`--override selection.max_quanta=null` は TOML 入力から「無し」を
  渡す唯一の口になる。ファイルに書く場合は項目ごと省略する。
- `modes` の CSV 参照（ADR-0019）は TOML では `modes = { path = "modes.csv" }` と書く。
  相対パスの基準は入力ファイルの位置のままである。
- `schema_version` は 2 に据え置く。書式が増えても読まれる構造は変わらないので、版で
  区別する理由がない。
