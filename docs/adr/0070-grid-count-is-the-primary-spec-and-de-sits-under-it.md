# グリッド数を主の指定とし、`de` をその下位に置く

- 日付: 2026-09-20
- 状態: 受理（ADR-0006 のうち「`de` を明示指定する」部分を差し替える）

FFT の基数は 2 の冪である。実装は前から `n_fft` を 2 の冪に丸めていたが（`envelope.py`
の `_next_pow2`）、その数は入力ファイルからは見えず、指定もできなかった。利用者が書けた
のは `de` だけで、実際に何点で変換したかは結果ファイルの診断値を見るまで分からない。

一方で `de` を書きたい理由も消えない。グラフの横軸の刻みが丸いほうが読みやすく、条件を
振った複数の計算で刻みを揃えたい場面もある。

そこで **`grid.points` をグリッド数の指定の場とし、`de` をその中の下位の書き方として
置く**。どちらか一方だけを書く。

```toml
[grid]
e_min = -4000.0
e_max = 1000.0

[grid.points]
n = 4096        # 点数を直接。2 の冪のみ
```

```toml
[grid.points]
de = 5.0        # 刻みから。これを満たす最小の 2 の冪が点数になる
shift = 1       # その冪を 1 段上へずらす
```

| 書き方 | 全域グリッドの点数 N | 全域幅 | 出力の ΔE |
|---|---|---|---|
| `n` | 書いた `n` | 窓ちょうど 2·e_half | 2·e_half / n（端数になりうる） |
| `de` | 2·e_half / `de` 以上の最小の 2 の冪 × 2^`shift` | N·ΔE（窓以上） | `de` / 2^`shift` |

`shift` は**全域幅を保ったまま**点数を増やす向きに効く。覆う範囲は変えずに刻みだけを
細かくするつまみである。逆向き（粗くする）は用意しない。粗くしたいなら大きい `de` を
書けばよく、同じことを 2 通りに書けるようにする理由がない。

## 帰結

`EnergyGrid` が持つのは解決済みの `(n_fft, de)` になり、2 の冪への丸めは
`EnergyGrid.from_points` / `from_spacing` に移る。`envelope.build_grids` は丸めも推定も
せず、渡された組をそのまま使う。値の型が自分の不変条件を持つ形は ADR-0051 のままで、
「全域グリッドは窓を覆う」もそこに加わる。

結果ファイルの入力エコーに `grid.n_fft` が増える。ΔE と N の両方がないとグリッドを
復元できないためである（`de` だけでは `shift` の入った格子を書き戻せない）。

`grid.de` が `grid.points.de` へ移るので、`schema_version` を 3 に上げ、2 は
`SchemaVersionError` で拒否する。互換層は置かない（ADR-0040 と同じ判断）。CLI の
上書きのキーも `--override grid.points.de=2.5` になる。書き方そのものを差し替えたい
ときはブロックごと渡す（`--override grid.points={"n": 4096}`）。

`n` の側は全域幅が窓ちょうどになるので、2 の冪への切り上げぶんの余白がある `de` の側より
端の折り返しが出やすい。点数を増やしたのに `edge_intensity_ratio` が悪くなることがあり、
これは覆う範囲が狭まったためである。

`shift` は**端の折り返し（`edge_intensity_ratio`）には効かない**。あの指標は全域幅で
決まり、`shift` は全域幅を変えないからである。窓を広げる向きの話はこの ADR の範囲外で、
警告文の助言（"Widen e_min/e_max"）をどう直すかは別に決める。

## 検討した選択肢

`n` を書いたときに `de` の併記を必須にして全域幅を `n·de` とする案も考えた。ΔE が丸い
ままになる利点はあるが、窓と全域幅の関係が入力から読み取れなくなる。`n` を書く動機は
「変換の点数をこの数に固定したい」であって、そのときに全域幅が窓ちょうどであるほうが
関係が単純である。丸い ΔE が要るなら `de` の側を書けばよい。

`n` が 2 の冪でないときに切り上げて受ける案も採らない。書いた数と実際に使う数が黙って
ずれるのは、点数を自分で決めたい利用者の意図に反する。2 の冪でなければその場で止める。
